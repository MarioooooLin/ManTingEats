# PRD — ManTingEats MVP

> 狀態：**已定案**（2026-09-16）。本文件記錄 MVP 範圍的產品需求，透過與使用者訪談確立。後續若模組擴充（例如加入庫存、外送 API 串接、多角色權限），請另開版本檔（例如 `v2.md`），不要覆蓋本文件。

## 1. 需求摘要

**目標**：建立單店家餐廳的內部管理系統，取代人工紙本作業，涵蓋點餐/結帳、訂位記錄、菜單管理、營收報表。

**使用者情境**：目前僅店長一人操作全部功能；未來可能新增服務生角色，帳號/權限設計需預留擴充空間。

**範圍界定**

- ✅ 本次做：菜單管理、點餐（內用含桌號 / 外帶）、簡易結帳、訂位記錄、營收報表（日期/品項/通路維度）
- ❌ 本次不做（列為未來擴充）：庫存管理、外送平台 API 串接、多角色細緻權限、發票開立、多元支付邏輯、桌位衝突檢查、訂位提醒、結帳找零計算

## 2. 模組詳細規格

### 2.1 菜單管理（Menu）

**使用者故事**

- As a 店長, I want 新增/編輯菜單品項與售價, so that 點餐時能選擇正確品項與金額。
- As a 店長, I want 將品項標記「售完/下架」, so that 顧客當天點不到已售完的品項。

**驗收標準**

- 品項需包含：名稱、分類、售價（必填，須 > 0）、上架狀態（啟用/停用）。
- 停用品項不會出現在點餐畫面的可選清單。
- 已被歷史訂單使用過的品項禁止硬刪除，僅能改為停用（避免歷史報表資料遺失）。

### 2.2 點餐與結帳（Order）

**使用者故事**

- As a 店長, I want 建立訂單並選擇通路（內用/外帶）, so that 可以正確記錄與統計業績。
- As a 店長, I want 對內用訂單填寫桌號, so that 可以在多桌同時服務時正確辨識加點對象。
- As a 店長, I want 在訂單結帳前持續加點, so that 同一桌可以分次點餐、系統自動重新計算總額。
- As a 店長, I want 完成結帳並記錄應收金額, so that 訂單狀態轉為已完成並計入營收。

**驗收標準**

- 訂單欄位：通路類型（內用/外帶）、桌號（僅內用必填，外帶留空）、品項清單（品項+數量+單價）、小計、總金額。
- 訂單狀態機：`未結帳（可加點）` → `已結帳（鎖定，不可再改品項）` → `已作廢`。
- 未結帳訂單可重複新增/移除品項、調整數量，金額即時重新計算。
- 結帳僅支援現金，系統只計算並顯示「應收總金額」，**不做找零計算**。
- 作廢已結帳訂單需記錄操作者與原因（稽核用途，避免營收被竄改而無紀錄）。
- 金額計算需使用 `decimal` 型別，禁止使用 `float`/`double`（避免精度誤差）。

### 2.3 訂位記錄（Reservation）

**使用者故事**

- As a 店長, I want 登記訂位的姓名、電話、人數、時段, so that 可以掌握當天的訂位狀況並依需求查詢。

**驗收標準**

- 訂位欄位：姓名、電話（格式驗證）、人數（正整數）、日期時段。
- 功能僅需要「新增」與「查詢」（依日期/姓名搜尋）。
- **不需要**：狀態追蹤（已到店/未到）、提醒功能、桌位衝突檢查。

### 2.4 營收報表（Reporting）

**使用者故事**

- As a 店長, I want 查看指定日期區間的總營收, so that 掌握每日/每月經營狀況。
- As a 店長, I want 依品項查看銷售排行, so that 了解哪些菜色最受歡迎。
- As a 店長, I want 依通路（內用/外帶）拆分營收, so that 了解各通路占比。

**驗收標準**

- 報表資料僅計入「已結帳」訂單，不含已作廢訂單。
- 支援自訂日期區間查詢（今日、本週、本月、自訂區間）。
- 品項統計顯示：銷售數量、銷售金額，可依金額排序。
- **不含外送業績**（外送平台自有終端機處理，金流不經過本系統；報表不需特別註記）。

### 2.5 帳號與權限（Auth）

**使用者故事**

- As a 店長, I want 登入系統, so that 只有授權人員可以操作訂單與查看營收。

**驗收標準**

- 帳號密碼登入，密碼須雜湊儲存（不可明碼）。
- 資料模型需可擴充角色欄位（例如 Role: Manager / Staff），本次僅實作 Manager 角色。

### 2.6 庫存管理（Inventory）— 本次不實作

- 資料庫設計時不擋未來擴充空間（例如未來可加 `InventoryItem`、`Recipe` 關聯表），本次不開發任何庫存 UI/邏輯。

## 3. 模組拆解與優先序

| 模組              | 相依關係                  | 優先序               |
| ----------------- | ------------------------- | -------------------- |
| Auth              | 無（最底層）              | 1                    |
| Menu              | 依賴 Auth                 | 2                    |
| Order             | 依賴 Menu、Auth           | 3                    |
| Reservation       | 依賴 Auth（獨立於 Order） | 3（可與 Order 並行） |
| Reporting         | 依賴 Order 的歷史資料     | 4                    |
| Inventory（未來） | 依賴 Menu                 | 之後再排             |

## 4. 已識別風險與因應

| 風險                                         | 因應                                                      |
| -------------------------------------------- | --------------------------------------------------------- |
| 加點時無法辨識是哪一桌                       | 內用訂單加入「桌號」欄位（自由文字/數字），不做正式座位圖 |
| 訂單作廢可能被濫用竄改營收                   | 作廢動作需記錄操作者與原因                                |
| 報表金額與店長實際總營收有落差（外送不計入） | 於使用情境教育層面說明，不在系統內特別處理                |
| 金額精度問題                                 | 一律使用 `decimal`，禁止浮點數                            |

## 5. 明確排除（未來擴充項目，非本次 MVP）

- 發票開立
- 多元支付方式（行動支付等）
- 外送平台 API 串接
- 桌位衝突檢查／正式座位管理
- 訂位提醒通知
- 結帳找零計算
- 庫存管理（原物料/成品）
- 多角色細緻權限（服務生角色的實際功能限制）
